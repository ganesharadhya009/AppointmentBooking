# Deferred Items & Attention List

Running log of everything flagged during development but not fixed immediately — either because it was correctly triaged as non-blocking, or because it's a forward-looking risk tied to a *future* sub-project rather than the one that surfaced it. Reviewed and updated at the end of each sub-project's final review. Intended to be worked through as a hardening pass once the core product (all Phase 1 sub-projects) exists end-to-end — not before, per YAGNI, but never silently dropped either.

Update this file whenever a final review (or any review) defers something. Each entry: what, where, why it matters, when to actually do it.

## 🔴 Must resolve before a specific future milestone (not just "someday")

- **Unit/integration test-writing deferred to a later consolidated pass, starting 2026-08-19.** Per explicit user instruction (cost/token concerns), remaining Phase 2+ sub-projects are being built functionality-first — production code, migrations, cross-service wiring — without new `[Fact]` test coverage, to be written in one or more dedicated later passes once functionality is far enough along. Every sub-project built under this mode ships with real, meaningful correctness risk (idempotency races, tenant-isolation edge cases, cross-service validation branches — exactly the classes of bug this session's test-first discipline caught repeatedly in earlier sub-projects) that nothing currently verifies. **Must be resolved (a real test-writing pass, service by service) before any of this code is treated as production-ready or exposed to real traffic.** Sub-projects shipped under this mode so far: `LeaveRequest` Task 2 (`DirectoryApi`, commit `5327285`), `RefundRequest` (`SchedulingApi`, commits `a86f909`/`bae4e76`), `SupportTicket` (`DirectoryApi`, commit `5450fc3`), `BillingApi` Wallet Foundation — `BillingApi`'s `Wallet`/`WalletTransaction` scaffold (commits `1174a9f`/`e04fa85`) and `SchedulingApi`'s refund-approval wallet-credit wiring (commit `8f8b052`), `BillingApi` Payment Gateway Integration — `WalletCreditService` extraction (commit `0be19e7`) and `PaymentGatewayTransaction`/checkout/callback endpoints (commits `9a2731f`/`9f518c4`), Phase 3 Reports — `SchedulingApi` filters/unified/cancellation report endpoints (commit `af728ec`) and `BillingApi` tenant-wide wallet transaction list/payment-checkout date filters (commit `29c8c8b`), `DirectoryApi` Banner/Poster/AppVersion (commits `2516401`/`da19791`), Phase 6 Today Summary — `DirectoryApi`'s active-leave-count endpoint (commit `f2a130c`) and `SchedulingApi`'s `GET /appointments/today-summary` (commit `fa14dd4`), **`ai-service` Enquiry Triage — `GET /enquiry-triage` (commit `8e3e1e2`, first Python sub-project under this policy)**. This closes Phase 2's backend scope — the eventual test pass needs to cover all of the above plus every Phase 3+ sub-project built the same way. **`BillingApi`/`SchedulingApi` wallet-credit wiring is the TOP PRIORITY item in this backlog: it is the platform's first real cross-service money movement (refund approval → parent wallet credit) and currently has zero test coverage of the idempotency-key path, the non-fail-open 502-on-credit-failure behavior, or the child→parent resolution branch — do this one first when the consolidated pass starts.** The payment-checkout callback's credited-but-still-`Initiated` crash window (see below) and its concurrent-redelivery race are the second priority, once the above is covered.

- **Three of the parent Phase 3 spec's six report types were explicitly scoped out of the Reports sub-project, not silently dropped — each needs a new persisted entity that doesn't exist yet.** (Flagged: Phase 3 Reports design spec §1, 2026-08-20.) Follow-ups, one per underlying feature:
  - **OTP audit report** — no OTP verification flow exists anywhere on this platform yet (auth is the `X-Tenant-Id` stub throughout). Build this only once real Auth0 work (deferred to the project's last phase) introduces an actual OTP step to audit.
  - **Therapist progress report** — no session-notes/progress-tracking entity exists on any service. Needs its own sub-project to define and build that entity first (likely `ClientRecordsApi`, alongside `Child`); the report itself is trivial once the data exists.
  - **Appointment swap/reschedule log** — `PUT /appointments/{id}`/`PUT /doctor-appointments/{id}` currently update the row in place with no audit trail. Needs a new write-side `AppointmentRescheduleLog`-shaped entity wired into both existing reschedule endpoints (a data-model change, not a pure read-only report) before any report over it is meaningful.

- **`BillingApi`'s payment-checkout callback uses a placeholder shared-secret header, not real gateway signature verification.** `POST /payment-checkouts/{id}/callback` (added in the Payment Gateway Integration sub-project, 2026-08-20) requires an `X-Gateway-Webhook-Secret` header matching a configured value — a stub-appropriate stand-in caught and self-fixed in response to a real automated-security-review finding ("anyone who can reach this endpoint could fabricate a Success callback and mint a wallet credit"), since there's no real gateway yet to verify an actual HMAC signature against. **Must be replaced with real provider signature verification (HMAC over the raw payload, using whatever scheme the eventual real `IPaymentGatewayClient` implementation's provider actually uses) before that real provider ships** — the shared secret is meaningfully better than nothing today but is not a substitute for real webhook authentication once real money starts flowing through a real gateway.

- **`X-Tenant-Id` is entirely client-supplied and unauthenticated.** Every service (`DirectoryApi`, `ClientRecordsApi`) trusts a plain header instead of a validated Auth0 token. Fine today — the only caller is the trusted admin SPA behind the gateway — but becomes a confused-deputy risk the moment one backend service calls another directly (nothing stops a caller from claiming to be any tenant). **Must be resolved (real Auth0-derived tenancy, or at minimum gateway-enforced header injection) before the Scheduling sub-project makes its first service-to-service call into `DirectoryApi` or `ClientRecordsApi`.** (Flagged: Client & Child Records final review, 2026-08-16/17.) **Escalated 2026-08-19 (BillingApi Wallet Foundation final review):** this gate has now been crossed into a money-moving service — `SchedulingApi`'s call to `BillingApi`'s `POST /wallets/{parentId}/credit` forwards a forgeable `X-Tenant-Id`, meaning any caller able to reach `BillingApi` directly (not just through `SchedulingApi`) can mint wallet balance for any tenant on a forged header. This is now the single strongest instance of the risk this item describes, not just a theoretical one — treat closing this as materially higher priority now that real money movement depends on it.

- **Reject-after-timeout can produce a genuine double credit on a refund (parked, not fixed — BillingApi Wallet Foundation final review, 2026-08-19).** If `SchedulingApi`'s call to `BillingApi`'s wallet-credit endpoint times out from the caller's perspective but actually committed server-side, `POST /refund-requests/{id}/approve` correctly returns `502` and leaves the refund `Pending` — and *retrying the same approve call* is safe (the downstream idempotency key is derived from the refund's own `Id`, so a retry replays instead of double-crediting). But nothing stops a human operator from instead rejecting the still-`Pending` refund and creating a **new** refund request for the same appointment (the create-endpoint's duplicate-guard treats `Rejected` as free-to-recreate) — that new refund has a different `Id`, hence a different derived idempotency key, hence a genuine second real credit once approved. **Ruling:** real gap, but narrow (requires an unlucky timeout window plus an operator choosing reject-and-recreate over retry) and the correct fix requires actual design work (an `AttemptedCredit`/`CreditConfirmedAt` field on `RefundRequest` that the reject/create-duplicate-guard endpoints check, or a reconciliation flow) rather than a quick patch — deliberately not rushed into the final review's one fix wave. **Must resolve before this platform's refund/wallet flow is exposed to real staff usage**, since it's a real (if narrow) money-safety hole. Documented in `docs/superpowers/specs/2026-08-19-billing-api-wallet-foundation-design.md` §4 as well.
- **Phase 4's Admin User Management and Tenant billing/onboarding are deferred, not part of the current Banners/Posters/AppVersion sub-project.** (Flagged: `docs/superpowers/specs/2026-08-20-directory-api-banners-posters-appversion-design.md`, user decision 2026-08-20.)
  - **Admin User Management** — provisioning back-office staff accounts is auth-adjacent (credential/role management); the parent spec (`docs/superpowers/specs/2026-08-18-phase4-platform-marketing-design.md` §2) itself frames this as blocked until real Auth0 work lands (deferred to the project's last phase). Build once real auth exists, not before — a credential-free stub was considered and explicitly not built (see the linked spec's scope decision).
  - **Tenant billing/onboarding** — needs a genuine business-model decision (self-serve signup vs. sales-assisted onboarding) that only the user can make, not a technical call. Ask when this sub-project is actually planned; do not assume either model.
- **M2M client-credentials token scoping** (one credential bound to exactly one `TenantId`, non-overridable) must be finalized before the Scheduling API is ever opened to an external B2B consumer. Not required until that phase starts. (Flagged: Phase 1 design spec §12.)
- **Known bug class still present in `DirectoryApi`, already fixed once elsewhere:** `UpdateTherapyTypeRequest.Status` (and likely other non-nullable enum/struct DTO fields across `DirectoryApi`) has the same `[Required]`-is-a-no-op problem that was found and fixed in `ClientRecordsApi`'s final review (nullable-DTO-field fix, commit `47030af`). `DirectoryApi` never got the equivalent fix. Concretely: omitting `status` on `PUT /therapy-types/{id}` or `PUT /therapists/{id}` where the entity isn't already `Deleted` may silently apply a default enum value rather than being rejected. Audit `TherapistDtos.cs`, `BranchDtos.cs`, `TherapyTypeDtos.cs` in `DirectoryApi` for every `[Required]` on a non-nullable value type and apply the same nullable-property fix.

## 🟡 Recommended hardening, do as one pass before Phase 1 ships

- **`SchedulingApi`'s booking-slot unique index hardcodes `AppointmentStatus.Cancelled`'s ordinal as a raw SQL literal.** `SchedulingDbContext`'s filtered unique index uses `.HasFilter("[Status] <> 2")` with no compile-time link to the enum — a future reordering of `AppointmentStatus` would silently repoint the filter at the wrong status with no compile error and no failing test, surfacing only as a real double-booking. Fix on the next migration touch: `.HasFilter($"[Status] <> {(int)AppointmentStatus.Cancelled}")` — identical resulting SQL, zero migration impact, just removes the hazard. (Flagged: Scheduling API final review + fix-wave re-review, 2026-08-17.)
- **`SchedulingApi` test coverage gaps from the Scheduling sub-project's fix wave:** `PUT /appointments/{id}` with a nonexistent id (404), `PUT` onto an already-booked slot (409), an `Idempotency-Key` header over 200 chars (400), and the `DbUpdateException`-unique-violation race path on both `POST`/`PUT` (409, with idempotency replay on the POST side). All are cheap tests cloning existing patterns in `AppointmentBookingTests.cs`/`AppointmentLifecycleTests.cs`. (Flagged: Scheduling API final review + fix-wave re-review.)
- **Process lesson for future plans (not a code defect):** the Scheduling final review's most consequential findings were a validation guard applied in `POST /appointments` (therapist-active check) that wasn't carried into `GET /availability` or `PUT /appointments/{id}`, even though PUT's Step 6 was written as a near-copy of POST's Step 5. When a future plan's later task copies an earlier task's validation chain, the plan should explicitly enumerate each guard and state whether it still applies — this would have caught the gap at plan-writing time instead of final review.
- **No `TenantId`-stamping safety net.** Every write handler across `DirectoryApi` and `ClientRecordsApi` independently does `TenantId = tenantContext.TenantId`. A future handler that forgets inserts an invisible, orphaned row. Recommended fix: override `SaveChangesAsync` in each `DbContext` to stamp `TenantId` on `Added` entities and throw if a tracked entity's `TenantId` doesn't match the current tenant. Highest-leverage single fix across the whole platform — do it once, in one place per service, before more services copy the current per-handler pattern. (Flagged: Client & Child Records final review.)
- **Every `Fake*ApiClient`'s mutable configuration properties (`FakeDirectoryApiClient.BranchToReturn`/`IsBranchClosedToReturn`/etc., `FakeClientRecordsApiClient.ChildToReturn`, now `FakeBillingApiClient.CreditResult` too) have no reset lifecycle in `LocalDbTestFixture`.** Since `IClassFixture` shares one fixture instance across every `[Fact]` in a test class, a test that sets a non-default value and a later test that doesn't explicitly reset it can silently inherit stale state. This exact bug already bit the Holiday sub-project once (fixed ad hoc with a per-test-class constructor reset, not centrally) and was independently re-surfaced by the BillingApi Wallet Foundation final review's fix-wave re-review (2026-08-19/20) while confirming `FakeBillingApiClient`'s registration matches the existing pattern — the leak risk is real but out of scope for that diff since it exactly mirrors the two already-accepted fakes, not a new hazard. Fix once, centrally: reset every fake's mutable properties to their defaults in `LocalDbTestFixture`'s constructor or an `IAsyncLifetime.InitializeAsync` override, across all four `LocalDbTestFixture` copies (`DirectoryApi`, `SchedulingApi`, `ClientRecordsApi`, `BillingApi`), instead of relying on each new fake avoiding the bug by accident.
- **`BillingApi`'s payment-checkout callback has a narrow credited-but-still-`Initiated` window.** `POST /payment-checkouts/{id}/callback`'s Success path calls `WalletCreditService.CreditAsync` (which commits its own transaction) and only then flips `PaymentGatewayTransaction.Status` to `Success` via a separate conditional update — a documented, reviewed, necessary split (nesting the credit inside one outer transaction throws in EF Core, since `CreditAsync` opens its own transaction on the same `DbContext`/connection). If the process crashes between those two steps, the wallet is correctly credited but the checkout row is left `Initiated` forever unless the gateway redelivers the callback (redelivery is self-healing: `CreditAsync`'s idempotency key finds the existing ledger row and the status flip completes on retry). Worth a periodic reconciliation sweep (`Initiated` rows older than N minutes, cross-checked against `WalletTransactions` by the derived idempotency key) once this moves past stub-gateway status. (Flagged: Payment Gateway Integration task review, 2026-08-20.)
- **All three `ai-service` HTTP clients (`directory_client.py`, `scheduling_client.py`, and now `client_records_client.py`) parse the response body OUTSIDE their `try/except httpx.HTTPError` block** — a malformed or schema-mismatched `200` response raises an unhandled `JSONDecodeError`/`pydantic.ValidationError` instead of failing open like the rest of the call. Every one of these clients' docstrings/callers assume "returns `[]`/`None` on any failure," so this is a real gap in that contract, not a hypothetical. Fix once, consistently, across all three (move `response.json()`/`.model_validate(...)` inside the `try`, catching `(httpx.HTTPError, ValueError)` or similarly broad) rather than ad hoc in whichever client is touched next. (Flagged: AI Service Enquiry Triage task review, 2026-08-20 — the gap is inherited from the two pre-existing clients, not introduced by that task.)
- **No fault-injection test coverage of the retry/transaction paths.** `DirectoryApi`'s Branch and Therapist `PUT` handlers went through two real fix rounds to get `CreateExecutionStrategy()` + `ChangeTracker.Clear()` correct — and nothing tests that correctness under an actual simulated transient failure, because LocalDB never produces one. Build an EF `DbCommandInterceptor`-based fault-injection harness (throw a transient-fault-shaped exception on the Nth command) — it closes this gap and the originally-deferred transaction-atomicity test in one piece of reusable infrastructure. (Flagged: Directory API — Therapist Management final review.)
- **No optimistic concurrency token (`RowVersion`)** on any entity in any service. Every `PUT` is last-write-wins. Add `[Timestamp] byte[] RowVersion` before production data exists — retrofitting after is a real migration against live data.
- **Deploy-time migration, not startup `Migrate()`.** Every service currently runs `db.Database.Migrate()` on startup. On Azure SQL this means the runtime SQL principal needs permanent DDL rights, and a bad migration crash-loops the container instead of failing a deploy step cleanly. Platform-wide decision needed (applies equally to `DirectoryApi`, `ClientRecordsApi`, and whatever `SchedulingApi` ships with) — move to a deploy-pipeline migration step before any real environment.
- **No batch/filtered lookup endpoints.** Neither `DirectoryApi` nor `ClientRecordsApi` has a `?ids=` filter on any list endpoint. The Scheduling sub-project will need to validate sets of Branch/Therapist/Child IDs and will otherwise be forced into N single-item cross-service GETs. Add `?ids=` support to the list endpoints these services already have, ideally before Scheduling starts (cheap now, annoying to retrofit once Scheduling depends on the current shape).
- **Soft-deleted/inactive records are invisible at the API boundary.** No list endpoint anywhere supports a `?status=` filter, and `GET .../{id}` returns `200` for an inactive/deleted row with no signal besides the `status` field itself. Every future consumer (Scheduling, in particular) must remember to check `status == Active` before acting on any referenced Branch/Therapist/Parent/Child. Either document this contract explicitly in each service's README, or add the filter.

## 🟢 Minor, fix opportunistically or ignore

- **Design decision, recorded for future reference: `DoctorAppointment`'s `PUT` (reschedule) re-captures `ConsultationFee` from the doctor's current record but deliberately does NOT re-capture `ConsultantClinicId`/`ConsultantServiceId`.** The implementation plan's own constraint text said all three should be re-captured; the final review caught the discrepancy. Ruling: the code is correct. Fee tracks current pricing (avoids stale cost on an active booking, same reasoning as `Appointment.PricePerSession`); clinic/service represent structural identity — if a doctor genuinely moves clinics/services, silently reassigning an already-booked appointment without staff review would be the wrong behavior, that scenario should be a cancel+rebook instead. The plan's constraint text was overly broad, not the implementation. (Flagged: Doctor Appointment Booking final review, 2026-08-19.)
- **`DoctorAppointment`'s `[Required]` on non-nullable `Guid` fields is a no-op** (`ConsultantDoctorId`/`ChildId` in `CreateDoctorAppointmentRequest`) — mirrors the identical, already-accepted pattern in `Appointment`'s own `CreateAppointmentRequest`. Harmless: `Guid.Empty` falls through to the cross-service lookup and yields a `ValidationProblem` anyway. (Flagged: Doctor Appointment Booking final review, 2026-08-19.)
- **`DELETE /doctor-appointments/{id}` has no status guard** — it will cancel a `Completed` appointment, while `PUT` explicitly blocks that transition. Identical to `Appointment`'s existing `DELETE /appointments/{id}` behavior — a pre-existing platform-wide pattern, not a regression.
- **No `PUT` tests for `ConsultantService`/`ConsultantClinic`/`ConsultantDoctor`**, and no dedicated cross-tenant `GET /consultant-doctors/{id}` test (tenant isolation for doctor lookups is only exercised indirectly via the FK-validation tests). Matches the plan's own test list verbatim, not an implementer gap — flagged for a coverage pass later. (Flagged: Consultant Catalog final review, 2026-08-18.)
- **`POST /enquiries/{id}/convert` has a TOCTOU race on concurrent double-conversion.** Two simultaneous convert requests against the same enquiry could both pass the `Status != Converted` check before either commits, producing two duplicate `Parent`/`Child` pairs. Consistent with the rest of the codebase's status-transition endpoints (none use a concurrency token either), not a new regression — but worth a shared fix (optimistic concurrency token) across all of them in one pass eventually. (Flagged: Enquiry Management final review, 2026-08-18.)
- **`Enquiry.Concerns`'s value-converter/comparer round-trip is under-tested** — the design spec called for empty-list/null round-trip tests and an in-place-mutation test (the exact scenario `ValueComparer` protects against); only a full-reassignment replacement test exists. The converter/comparer are correctly wired; the gap is test coverage, not implementation. (Flagged: Enquiry Management final review.)
- **`ai-service`'s `GET /enquiry-triage` "follow-up due today" scoring bonus uses floor-based `timedelta.days` arithmetic**, so it only actually fires for a follow-up date within the past ~24 hours, not any time later on the current calendar day. A design-spec nuance carried from the plan text itself, not an implementer bug — low impact on a heuristic priority score. (Flagged: AI Service Enquiry Triage task review, 2026-08-20.)
- **`ai-service`'s `GET /suggestions` calls `SchedulingApi` sequentially per candidate therapist**, not concurrently (`asyncio.gather`) — fine for a stub at current scale, would add latency once branches have many therapists. (Flagged: AI Service Slot Suggestion Stub review, 2026-08-17.)
- **`ai-service`'s HTTP clients construct a fresh `httpx.AsyncClient()` per call** rather than reusing a pooled client — minor inefficiency, not a correctness issue.
- **No logging on `ai-service`'s swallowed downstream-failure paths** (`DirectoryApiClient`/`SchedulingApiClient` returning `[]` on any error) — fine for MVP, would hamper debugging once this moves past the stub stage; add structured logging before Phase 7 builds real AI features on top of this pattern.
- **No test covers a mixed partial-failure scenario** for `GET /suggestions` (one candidate therapist's `SchedulingApi` call fails while another succeeds) — existing tests cover total failure (empty result) and total success, not the in-between case that most directly proves per-therapist exclusion.
- **`ai-service` has no Alembic/migration tooling yet** — `SlotSuggestionLog` exists as a SQLAlchemy model with no path to a real Postgres table. Needs a migration setup before this service is ever pointed at a real Postgres instance.

- All 6 GitHub Actions workflows trigger `push` on `branches: [main]`, but the repo's actual branch is `master` — push-time CI re-validation never fires, only `pull_request` validation works. One-line fix per workflow file whenever touched next.
- `infra/bicep/main.bicep`'s Key Vault name would overflow the 24-char limit if `environmentName` is ever set to something longer than `dev`/`staging`/`prod`.
- Leftover default Vite boilerplate in the Admin SPA (unused demo CSS/assets from scaffolding) — cosmetic, no functional impact.
- No DB-level FK from `Branch.TenantId`/`TherapyType.TenantId`/etc. to `Tenants.Id` — any GUID header creates a working (if bogus) tenant partition. Low priority since query-filter isolation already holds; would only matter for referential-integrity reporting.
- `Tenant.SubscriptionStatus` is written but never enforced — a `Suspended`/`Cancelled` tenant currently has full API access. Needs an actual auth/billing sub-project to make meaningful.
- No `.AsNoTracking()` on read-only `GET` queries across any service — negligible at current scale, worth doing in a pass once traffic patterns are known.
- No unique DB index on `TherapistAssignment` `(AssignmentId, WindowName)`, and no index on `BranchId`/`TherapyTypeId` — the app-level validator currently enforces the invariant; add the index for defense-in-depth once Therapist scheduling queries are designed.
- `SessionWindowDto` has no `Id` in API responses — would need adding if a future per-window update API is ever built.
- `LocalDbTestFixture.DisposeAsync` shadows (`new`) rather than overrides the base `IAsyncDisposable.DisposeAsync` — correct under xUnit's `IAsyncLifetime`, but any path disposing via plain `IAsyncDisposable` would skip `EnsureDeletedAsync()` and leak LocalDB test databases. Present identically in all 4 services now (`DirectoryApi`, `ClientRecordsApi`, `SchedulingApi` — copied pattern) — fix once, propagate to the others if worth the churn.
- Pagination clamp/envelope logic (`page <= 0 ? 1 : ...`, `Math.Min(pageSize, 100)`) is duplicated verbatim across every endpoint file in every service — **now 4 call sites** (`SchedulingApi`'s `GET /appointments` is the 4th) per the threshold this doc originally set ("extract once a 4th or 5th resource makes the duplication actually costly"). That threshold has been crossed; worth extracting a shared helper in the next hardening pass rather than deferring further. (Flagged: Scheduling API final review.)
- No OpenAPI/Swagger metadata (`.Produces<T>()`, `.WithName()`) on any endpoint anywhere — worth adding before the Admin SPA needs a stable, discoverable contract to code against.
- **`GET /appointments/today-summary` computes "today" as server UTC (`DateOnly.FromDateTime(DateTimeOffset.UtcNow.DateTime)`), not tenant/branch-local time.** No other endpoint on this platform is timezone-aware either, so this is consistent with the rest of the codebase, not a new gap — but a KPI dashboard literally titled "today" is the first place this will visibly matter (a branch in a timezone ahead of UTC sees "yesterday's" completed appointments still counted as "today" until UTC midnight, or vice versa behind UTC). Worth a platform-wide timezone pass once any client actually displays this. (Flagged: Phase 6 Today Summary design spec, 2026-08-20.)
- GUID primary keys use `Guid.NewGuid()` (random), meaning default clustered-index insert patterns will fragment under real write volume on Azure SQL. Consider `NEWSEQUENTIALID()` as a DB default, or non-clustered PKs, once real traffic volume is a concern — not before.
- **`Wallet.Balance` (`decimal(10,2)`) has no overflow handling.** A running balance that would exceed `99999999.99` raises a raw SQL arithmetic-overflow error (`SqlException` 8115), which `BillingApi`'s narrow unique-violation catch (`2601`/`2627`) doesn't cover — surfaces as a 500, which `SchedulingApi` turns into a 502 that never converges on retry. Extremely unlikely at any realistic wallet balance; noted for completeness. (Flagged: BillingApi Wallet Foundation final review, 2026-08-19.)
- **A child reparented to a different `Parent` between a failed refund-approval attempt and its retry produces a permanent 502.** The derived downstream idempotency key (`refund-approve:{refundRequest.Id}`) stays the same, but the resolved `ParentId` changes — `BillingApi`'s idempotency-mismatch check correctly rejects the mismatched replay, but that means the retry can never succeed as-is. Requires a genuinely rare sequence (reparenting mid-flight); noted for completeness. (Flagged: BillingApi Wallet Foundation final review, 2026-08-19.)
- **`RefundRequestEndpoints`'s new duplicate-active-request guard has a benign TOCTOU** (same class as the Enquiry-convert race already logged above): two simultaneous `POST /refund-requests` for the same appointment could both pass the `AnyAsync` check before either commits, producing two active refund requests. Self-fixed alongside the missing `Amount` positivity check (commit `bae4e76`, in response to the automated security review's real "double-spend" finding) but the check itself isn't concurrency-safe; would need a DB-level partial-unique-index (`WHERE Status <> 'Rejected'`) to close for real, deferred with the rest of this class of race.
- **`SupportTicketMessage.Body`/`SupportTicket.Category`/`Title` have no upper bound on `Body`** (unlike `Category`/`Title`, which are `MaxLength(200)`) — an unbounded conversation message body. Fine for now (no DB column-length crash since it maps to `nvarchar(max)` by default), but worth a sane cap (e.g. 4000 chars) once the Admin SPA's support-ticket UI is built, to prevent pathological payloads.
